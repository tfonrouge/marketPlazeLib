# Decision Ledger — MercadoLibreIntegration

| Date | Decision | Type | Rationale | Evidence required to revisit |
|------|----------|------|-----------|------------------------------|
| 2026-07-03 | **D1**: Reactivate the bridge (⏸️ Deferred → 🟡 Active) and expand its scope to include push, not just the originally-scoped `fetchProducts` client | APPROVED | The stated reactivation trigger ("consumer commits to providing OAuth2 token-refresh flow and endpoint priorities") was already satisfied — mppErsaPack has OAuth2 PKCE + refresh working in prod since 2026-05-13 (its own LEDGER D42). Push was never explicitly excluded from the original BRIEF's Out of Scope list, so expanding scope is additive, not a redefinition | MercadoLibre deprecates the global API host or the PKCE flow mppErsaPack relies on |
| 2026-07-03 | **D2**: This increment ships push only (`updateAvailableQuantity`). Migrating the existing read-side `MercadoLibreApiClient` (fetchProducts/fetchOrders/OAuth) from mppErsaPack into this library is explicitly deferred to a separate future bridge/decision | APPROVED | That migration touches live prod-serving code in a different repo and carries real risk (token rotation is single-use and environment-sensitive per mppErsaPack LEDGER D42's dev/prod coexistence rule) — bundling it with the push feature would inflate blast radius for no shipping benefit | A consumer needs the read-side client from the library too (e.g. a second app integrating MercadoLibre), making the duplication costly enough to justify the migration risk |
| 2026-07-03 | **D3**: HTTP client = Ktor (CIO engine), not `java.net.http.HttpClient` | APPROVED | mppErsaPack's existing `MercadoLibreApiClient` already uses Ktor CIO for all MercadoLibre REST calls — matching it keeps the eventual read-side migration (D2, if it happens) low-friction. `java.net.http.HttpClient` is only used elsewhere in this repo for one Shopify multipart-upload edge case, not as the general pattern | Ktor client adds a dependency this library didn't previously carry (mercadoLibreLib's `jvmMain` had zero external deps before this); if that dependency ever conflicts with a consumer's own Ktor version pin, reconsider |
| 2026-07-03 | **D4**: The engine does not retry after refreshing an expired token — 401 is surfaced as an error, full stop | APPROVED | Token refresh is stateful (persists rotated tokens to MongoDB) and environment-sensitive (mppErsaPack LEDGER D42: refresh tokens are single-use, dev and prod refreshing independently invalidates each other). This library has no MongoDB dependency today and should not gain one just to own refresh | A second consumer needs refresh-and-retry baked into the library; design a pluggable refresh callback rather than hardcoding MongoDB persistence |
| 2026-07-03 | **D5**: This bridge's `.blueprint-status` stays `ACTIVE`, not `STABLE`, until a real consumer in mppErsaPack calls `IMercadoLibrePushService` | APPROVED | Direct precedent in this same repo: `IShopifyPushService`/`ShopifyPushEngine` shipped 2026-03-16 (`ShopifyPushSync(BRIDGE)`, marked ✅ Complete) and is **still unused** by mppErsaPack as of this session — `grep -rln "ShopifyPushEngine\|IShopifyPushService" mppErsaPack/ersaPack mppErsaPack/ersaPackLib` returns zero matches. mppErsaPack's real `pushInventoryToShopify()` reimplements Apollo calls inline instead. Marking a library capability "Complete"/"Stable" without a consumer let that drift go undetected for 4 months (see `ShopifyPushSync(BRIDGE)/AUDIT.md` drift log, added this session). Repeating that for MercadoLibre defeats the purpose of building the capability | mppErsaPack ships `pushInventoryToMercadoLibre()` calling `IMercadoLibrePushService` — flip to `STABLE` at that point, referencing the mppErsaPack commit/PR |
| 2026-07-03 | **D6**: `MercadoLibrePushEngine` accepts an optional injected `HttpClientEngine` (test seam), diverging slightly from `ShopifyPushEngine`'s pattern (which has no injection point and is untested directly — only exercised indirectly via `SyncEngineTest`'s fake `IShopifyPushService`) | APPROVED | MercadoLibre push has no higher-level orchestration engine yet to fake-test through (unlike Shopify's `ShopifyBidirectionalSyncEngine`) — without the injection seam, the only way to test `MercadoLibrePushEngine` itself would be a live API call. The seam is a production no-op (defaults to real CIO) | An orchestration engine analogous to `ShopifyBidirectionalSyncEngine` gets built for MercadoLibre push — at that point, consider whether direct engine tests are still needed or the fake-interface pattern supersedes them |
| 2026-07-03 | **D7**: `updateAvailableQuantity` builds and closes a fresh `HttpClient` on every call — no connection/client reuse across calls (found via adversarial review 2026-07-03) | ACCEPTED, not fixed | Matches the existing `ShopifyPushEngine` precedent exactly (every one of its 10 methods also builds+closes its own `ApolloClient` per call — see `ShopifyPushEngine.kt`). MercadoLibre's REST API has no bulk stock-update endpoint (BR-05), so a bulk consumer must make N HTTP calls regardless; the open question is only whether those N calls share one client. Building that reuse path now, with no real consumer yet, would be speculative — the exact shape (shared client injected once vs. an internal pool) should be decided against the actual bulk-push orchestration code when mppErsaPack builds it, not guessed in advance | A consumer profiles a bulk push (dozens–hundreds of items) and per-call CIO client creation shows up as a measurable bottleneck — at that point add a reuse path (e.g. `MercadoLibrePushEngine(sharedClient: HttpClient)` that the caller owns and closes), mirroring how ErsaPack's real Shopify push builds one `apolloClient` outside its batch loop instead of calling `ShopifyPushEngine.updateInventory()` per item |
| 2026-07-03 | **D8**: Fixed two real (not speculative) issues found by an independent audit pass: (a) the error-body handling path called `response.bodyAsText()` twice — a second read that Ktor's `MockEngine` tolerated in testing but is not a documented-safe operation on a real `HttpResponse`; (b) when MercadoLibre's error body was not valid JSON (e.g. an HTML gateway page on 502/503), the JSON-parse exception replaced the error message entirely, losing the HTTP status code from `SimpleState.msgError`. Fix: read the body once into a local, and wrap only the JSON-parse attempt in its own `try`/`catch`, falling back to the raw body text (with the HTTP status still prefixed) on parse failure | APPROVED | Verified empirically before fixing (2 throwaway probe tests confirmed neither path crashed, but the non-JSON case produced a diagnostically weaker message than necessary — `msgError` read as a bare Kotlin serialization exception with no HTTP status). Both probes were converted into permanent regression tests rather than discarded. Test count: 4 → 6 | A future refactor reintroduces a second `bodyAsText()` call on the same response, or drops the try/catch around the JSON-parse-of-error-body — both would silently regress this fix; the 2 regression tests exist specifically to catch that |
